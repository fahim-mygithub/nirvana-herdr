  Their workers started in `wS:pV` and `wS:pW`, tab `wS:t2`. The `seated` event records no pane. Nothing in the

## The cause, step by step

1. `replay`'s `Kind::Opened` arm keeps only the first `opened` (`if state.opened.is_none()`). Confirmed.
2. `seat_order_with` builds an `opened` with `HERDR_PANE_ID`, and `seating` writes it only when the run has none.
   Confirmed. So a later `seat run` from another pane recorded nothing.
3. Every reader took `opened.orchestrator_pane`: `wake_once` (`nirvana_run.rs`), `last_end_of` and `open_of`
   (`nirvana_fresh.rs`), and `read_seat_orders` (`nirvana_subagents.rs`). Confirmed. No reader outside `src/` or in
   `nirvana/claude` reads the field.
4. `pane_view` read every failure of `pane get` as `PaneProgram::Unknown`, which is "herdr could not say what runs in
   it". Confirmed. herdr answers a pane it does not have with error code `pane_not_found` (`app/api/panes.rs`,
   `pane_not_found()`), on stderr. That `wH:p1` was gone today is inferred: `Unknown` also comes from a herdr that
   did not answer, or from a failed `process-info`. Per the order, I made no probe of the owner's herdr.

## What was built

- A new journal kind, `orchestrator_moved {pane, from}`. `seating` writes it before `seated` when the run is opened
  and the `seat run`'s `HERDR_PANE_ID` is set, differs from the current pane, and is none of the run's own worker
  panes. `replay` keeps `RunState.orchestrator_pane`, which is the first `opened`'s pane or the latest move.
  `opened.orchestrator_pane` stays the pane the run began in. Why a new kind and not a second `opened`: `opened` holds
  the run's start and its pools, and its first-only rule is what old journals rely on. A herdr before this fix reads
  the new line as `Unknown` (`#[serde(other)]`) and keeps the first pane, which is how it behaved before.
- All four readers now use `state.orchestrator_pane`.
- `PaneProgram::Gone(pane)`. `herdr_json_coded`, with the pure `herdr_error`, keeps herdr's error code. `pane get`
  answering `pane_not_found` gives `Gone`, and every other failure stays `Unknown`. A gone pane queues with "the
  orchestrator's pane wH:p1 is gone: herdr no longer has it; a seat run from Nirvana Claude's pane moves the run
  there". `type_if_nirvana` refuses it, naming the pane. A wake still types only into `NirvanaClaude`.
- Item 3, the retry: no new code. A queued wake goes on the retry list (plan 31 review W). The server's pass runs
  `herdr run wake` every 30 s, backing off to every 300 s, with no cap on tries. That wake replays the journal, so
  the first retry after the move targets the new pane. A wake fired at the move itself would only queue: the
  orchestrator is mid-turn (`working`) while its `seat run` runs. Test `wake_pane_a_queued_wake_is_retried_toward_
  the_new_pane` shows the retry follows the move.

## Which commands move the run

Only `seat run`, including `herdr profile teach`, which seats through the same `seat_order_with`. These were not
made to move it:
- `run notice` without a run id reads every run of the project. Moving on it would hand every run to whichever
  Nirvana Claude prompts next.
- `run log` (gated/merged/asked by hand) and `run end` both name a run, but nothing has shown they come from a new
  pane. `run end` matters only to the fresh start. Hypothesis: a run that a new pane only ends, without seating into
  it, keeps the old pane for the fresh-start rule.
- No `run open` verb exists.
