## The cause, step by step

1. `replay`'s `Kind::Opened` arm keeps only the first `opened` (`if state.opened.is_none()`). Confirmed.
2. `seat_order_with` builds an `opened` with `HERDR_PANE_ID`, and `seating` writes it only when the run has none.
   Confirmed. So a later `seat run` from another pane recorded nothing.
3. Every reader took `opened.orchestrator_pane`: `wake_once` (`nirvana_run.rs`), `last_end_of` and `open_of`
   (`nirvana_fresh.rs`), and `read_seat_orders` (`nirvana_subagents.rs`). Confirmed. No reader outside `src/` or in
   `nirvana/claude` reads the field.
4. `pane_view` read every failure of `pane get` as `PaneProgram::Unknown`, which is "herdr could not say what runs in
   it". Confirmed. herdr answers a pane it does not have with error code `pane_not_found` (`app/api/panes.rs`,
   `pane_not_found()`), on stderr. That `wH:p1` was gone today is inferred: `Unknown` also comes from a herdr that
   did not answer, or from a failed `process-info`. Per the order, I made no probe of the owner's herdr.

## What was built

- A new journal kind, `orchestrator_moved {pane, from}`. `seating` writes it before `seated` when the run is opened
  and the `seat run`'s `HERDR_PANE_ID` is set, differs from the current pane, and is none of the run's own worker
  panes. `replay` keeps `RunState.orchestrator_pane`, which is the first `opened`'s pane or the latest move.
  `opened.orchestrator_pane` stays the pane the run began in. Why a new kind and not a second `opened`: `opened` holds
  the run's start and its pools, and its first-only rule is what old journals rely on. A herdr before this fix reads
  the new line as `Unknown` (`#[serde(other)]`) and keeps the first pane, which is how it behaved before.
- All four readers now use `state.orchestrator_pane`.
- `PaneProgram::Gone(pane)`. `herdr_json_coded`, with the pure `herdr_error`, keeps herdr's error code. `pane get`
  answering `pane_not_found` gives `Gone`, and every other failure stays `Unknown`. A gone pane queues with "the
  orchestrator's pane wH:p1 is gone: herdr no longer has it; a seat run from Nirvana Claude's pane moves the run
  there". `type_if_nirvana` refuses it, naming the pane. A wake still types only into `NirvanaClaude`.
- Item 3, the retry: no new code. A queued wake goes on the retry list (plan 31 review W). The server's pass runs
  `herdr run wake` every 30 s, backing off to every 300 s, with no cap on tries. That wake replays the journal, so
  the first retry after the move targets the new pane. A wake fired at the move itself would only queue: the
  orchestrator is mid-turn (`working`) while its `seat run` runs. Test `wake_pane_a_queued_wake_is_retried_toward_
  the_new_pane` shows the retry follows the move.

## Which commands move the run

Only `seat run`, including `herdr profile teach`, which seats through the same `seat_order_with`. These were not
made to move it:
- `run notice` without a run id reads every run of the project. Moving on it would hand every run to whichever
  Nirvana Claude prompts next.
- `run log` (gated/merged/asked by hand) and `run end` both name a run, but nothing has shown they come from a new
  pane. `run end` matters only to the fresh start. Hypothesis: a run that a new pane only ends, without seating into
  it, keeps the old pane for the fresh-start rule.
- No `run open` verb exists.

## Review round, 2026-11-01

The review (`wake-review.md`, Sonnet high) checked against the code before building. Every finding held; none was
wrong. One claim in it was imprecise: S1 says the probe goes "near nirvana_worker.rs:3745, where `opened` is built",
which is right, but a probe there on every `seat run` would cost two herdr calls per seat; it is asked only when a move
is due (below).

- **S1, built.** `nirvana_worker::mover` reads the journal before the lock and asks herdr (`pane_get`, the wake's own
  reader) what runs in the caller's pane only when `orchestrator_move` says a move is due. Only `NirvanaClaude` moves
  the run; `Other` (a shell, plain Claude Code), `Unknown` (herdr did not answer) and `Gone` write no move. Under the
  lock, `seating_from` decides the move again on the events it follows, so a race only drops a move, never writes a
  stale one. A seat from the orchestrator's own pane, from outside herdr, or into a run not yet opened asks herdr
  nothing. `seating` is back to master's body. The first `opened` still records `HERDR_PANE_ID` whatever runs there,
  as before: the program check is for taking a run from a pane that has it, not for starting one.
- **S2, built.** `RunState.orchestrator_panes` keeps every pane that has held the run. `open_of` (the fresh start's
  "never /clear in the middle of a run" guard) counts a pane the run moved away from while the run is open: a live
  Nirvana Claude may still sit there (S3). It fails safe, as a run left open by mistake does. `last_end_of` stays the
  current orchestrator's only: the pane the run moved to is the one that saw its end.
- **S3, recorded.** Two Nirvana Claudes seating into one run in turn is unsupported. The run flips on each move; each
  wake goes to the latest seater, and the other gets the notice route on its next prompt. Nothing prevents it.
- **S4, covered by S1.** A worker's pane from an earlier attempt, or a worker of another run, runs a seat CLI under
  `seat exec`, not Nirvana Claude, so `pane_get` reads `Other` and no move is written. This rests on `pane_program`'s
  rule (the `--agent nirvana` mark), not on a test of a worker pane reading `Other`.
- **N1, built.** `herdr_error` takes the first of stdout and stderr that holds an `error` object, stdout first.
- **N2, recorded.** The older-herdr claim stays argued, not run: no test parses the new line with an enum lacking the
  variant. Mixed binaries are real here (owner daemon vs per-pane binary). An older binary's `seat run` from a new
  pane writes no move, and an older reader of a moved journal wakes the first pane. Transitional.
- **N3.** The Gone reason ("a seat run from Nirvana Claude's pane moves the run there") is now true as written: only
  a pane shown to run Nirvana Claude moves the run. Kept.
- **N4, recorded.** That `wH:p1` was gone in the incident is still inferred. Do not close the incident as proven
  until a wake on f2u-setup after this fix lands reads `Gone` or types.
- **N5, built.** `seating_from` writes the move even when the order id is known (no second `seated`): a resumed
  orchestrator in a new pane that re-issues its order ids gets its wakes.

Untested: the `HERDR_PANE_ID` read and the `mover` call inside `seat_order_with` itself. The tests reach `mover`,
`seating_from` and `pane_get_with` directly; `seat_order_with` needs a booked seat and launches a worker, and setting
`HERDR_PANE_ID` in a test is process-wide.
