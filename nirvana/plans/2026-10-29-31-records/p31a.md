## §2.3 root cause: what the evidence proves and what it does not

Evidence was read only: the journals of `dune-v5`, `dune-v5b` and `dune-v6`, Nirvana Claude's transcript
`04be6454-...jsonl` (55 MB, streamed), and herdr's server log `%APPDATA%\herdr\sessions\nirvana\herdr-server.log`.

1. **Every late case had one wake attempt, and it typed nothing.** At each of the four worker ends (06:43:27Z,
   12:33:10Z, 13:04:16Z and 20:28:21Z), the server log has the worker pane's `agent changed ... agent=None` and no
   `agent.prompt` request. At every prompt wake that worked (03:19Z to 04:07Z, and 21:04:03Z), the log has
   `cli:agent:prompt` in the same second. No `api.request.fail` was logged, and a failed request would log at info. So
   `wake_decision` returned `Queue`, or `type_prompt` found the pane not Nirvana Claude.
2. **Nothing retries a queued wake.** The only callers of `nirvana_run::wake` are the worker supervisor at an order's
   end, a rate limit or a stall, and `herdr run tick`. No hook, server loop or guidance runs `tick`. "retried later"
   in `wake_decision` is a promise no code keeps. A queued event therefore waits for the owner's next prompt (the
   `UserPromptSubmit` notice) or another worker's end in that run. Each of the four runs had one worker at a time.
   This is the proven cause of the waits' length: 20,275 s, 1,506 s, 25,798 s and 1,132 s.
3. **Which rule queued is not recorded anywhere.** `seat exec` drops the verdict (`let _ = nirvana_run::wake(...)`).
4. Ruled out:
   - **The daemon version.** One server process, pid 61704, started 03:16:28Z, served the working wakes and the four
     failures, with no restart between. The digest said "Nirvana 0.43.0" at 03:16Z and at 13:53Z.
   - **Plan 25's fresh start.** Every Stop hook in those stretches printed "no fresh start ... run dune-v5b of this
     pane is open".
   - **Plan 27's idle compact.** No `/compact` is typed in the transcript in any of the four stretches. The one
     compaction, at 13:53:06Z, is Claude Code's own ("Compacted while idle, before the prompt cache expired"), after
     the 13:04:16Z attempt.
5. A correlation, not a proof:
   - **The four failures.** Each followed an owner prompt that reached Claude Code through its command queue while
     the session was idle: a `queue-operation enqueue` line just before the prompt, at 06:34:53Z, 12:20:39Z,
     12:57:47Z and 20:13:44Z. Remote Control was active ("/remote-control is active", 03:16:36Z), so these look like
     prompts from the phone.
   - **The successes.** Across the transcript's 53 typed wakes, 50 followed a prompt typed straight in. One followed an
     idle-queued prompt (2026-10-24 04:48:02Z), so the correlation is not a law.
   - What a phone prompt would change on the pane is unknown. The candidates are herdr's agent status, the prompt line
     `prompt_line_text` reads, and the process view. No screen of the pane at those times exists.

**Built:** the `wake_queued` record, so the next occurrence names its rule. No retry and no screen-rule change: either
one would fix a cause that is not proven.

### Where the order was wrong or silent

- S3 names `agent send-text`. herdr has no such command or method (`src/api/schema.rs` has `agent.send_keys` only).
  `agent send-keys` is guarded; `agent prompt` is not, as the wake uses it.
- S2's escape is an env var only `herdr_self` sets, but the server cannot see a caller's env. The CLI turns the env var
  into the request's `force` field, which the `--force` flag sets too. Any socket client can therefore pass
  `force: true`: an explicit bypass, not an accident.
- `--force` must come before the text on `pane send-text`; after it, it is read as part of the text (the test found
  it).
- B1's "every doubt refuses" with N3: `--send-ok` on an order granted no device server is refused, not seated with an
  approval no line tells its worker. The audit's three Sends were all `needs: []` orders; they would now need `--needs`.
- W's "delivered once": the journal's `woken` events were already the delivery record (`woken_through`), and the notice
  already checked it under the journal lock. The gap was the wake, which read the queue, then typed. It now reads again
  under the lock just before typing. It does not hold the lock while typing: the typed digest fires the
  `UserPromptSubmit` hook, whose notice takes the same lock under a 10 s timeout.
