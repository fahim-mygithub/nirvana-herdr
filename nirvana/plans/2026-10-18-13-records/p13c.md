# Plan 13 P3 (p13c): the session record and the memory trim

Builder: Sonnet 5.5 high. Branch `p13c-memory`, from master 2cdc8bcd. Spec: `plans/2026-10-18-13-smart-preload.md` §6.1's
record, §6.2, §7's `herdr memory`, §8's file split.

## What was built

- `src/nirvana_session_record.rs` (new): `herdr memory record-session`. Reads a hook's JSON on stdin and writes
  `<home>/nirvana/sessions/<folder_hash>.json` as `{"session_id", "at", "transcript"}` (RFC 3339 UTC), through a
  temporary file and a rename. Always exits 0; a bad stdin, a subagent's hook (`agent_id`), a missing or odd
  `session_id`, a relative `transcript_path` or an unwritable home writes nothing. `read` is the same reading P1's
  launch needs; P1 may use it or read the file by its fixed format.
- `src/nirvana_memory_trim.rs` (new): the folder encoding and the index path, `status`, `propose`, `accept`, `discard`,
  `restore`, the pointer check, the `Trimmer` trait with the live `JevTrimmer`, and the `herdr memory` command.
- `src/main.rs`: two `mod` lines and a `memory` dispatch arm.
- `nirvana/claude/hooks/hooks.json`: `memory record-session` added to the `SessionStart` group (after `nirvana digest`)
  and the `Stop` group (after `nirvana stop`), same exec form, timeout 10.
- `nirvana/controls.d/p13c.py`: the controls (`python nirvana/controls.py --dry-run` counts them). `nirvana/CHANGELOG.md`: the entry `alpha NEXT (p13c)`.

## The interface P2 calls (all in `nirvana_memory_trim`)

- `status(cwd: &Path) -> Option<TrimStatus>`; `TrimStatus { index, tokens, limit, over, proposal:
  Option<ProposalStatus { tokens, saved }>, backup: Option<PathBuf> }`. `None` when the folder has no auto memory index.
- `propose(cwd) -> Result<TrimStatus, String>`; `accept(cwd) -> Result<Accepted { backup, before, after }, String>`;
  `discard(cwd) -> Result<bool, String>` (`false`: there was none); `restore(cwd) -> Result<PathBuf, String>`.
- Each has an `_in(ctx, ...)` form taking a `Ctx { home, projects, limit }`, which is what the tests use. `propose_in`
  also takes a `&dyn Trimmer`, so a test hands it any text.
- `Ctx::from_env()`: `NIRVANA_HERDR_HOME`; the projects folder is `NIRVANA_CLAUDE_PROJECTS_DIR` or
  `<CLAUDE_CONFIG_DIR or ~/.claude>/projects`; the limit is `NIRVANA_TRIM_OVER_TOKENS`, else `trim_over_tokens` at the top
  of `<home>/nirvana/preload.toml` (P1's file, read only), else 4,000.
- A token is bytes over four (`nirvana_jev::content_tokens`), the same rule the Jev log uses. The panel's own reading of
  MEMORY.md comes from `/context`; the two differ (plan §1 reads 7.8k for a file this rule counts lower), so `over` is
  an estimate.

## Measured

- **Which folder a hook sees** (`claude -p`, Claude Code 2.1.302, hooks dumping stdin and env to a file, scratch folder
  `proj`, one Bash call `cd sub`): `SessionStart` got `cwd = proj`; `Stop` got `cwd = proj\sub`. `CLAUDE_PROJECT_DIR` was
  `proj` (forward slashes) at both events. The brief's claim that a session started in a subfolder still reports the folder
  `nirvana window` opened is wrong once the session changes directory. The record uses `CLAUDE_PROJECT_DIR`, then `cwd`.
  The hook process also runs with the hook's `cwd` as its own working directory. Not measured: a session whose Claude
  was started in a subfolder by the owner (that is a different project dir, so a different record, which is right).
- **Folder encoding**, read from the real `~/.claude/projects` names: every character that is not an ASCII letter or digit
  becomes `-` (`C:\Users\fahim\.nirvana\x` is `C--Users-fahim--nirvana-x`; `\\wsl.localhost\Ubuntu-24.04\...` is
  `--wsl-localhost-Ubuntu-24-04-...`). All 172-character-or-shorter names found contain only letters, digits and `-`.
  Claude Code's rule for names over 200 characters is not known; `index_path` returns `None` rather than guess.
- **Live Jev, 2 calls** (limit 2), on a copy of the owner's largest MEMORY.md (the 3D-Printer-Flow project's, 17,694 bytes,
  116 entries) placed in a scratch projects folder under `target/p13c-e2e`, with the limit at the default 4,000 and the
  binary's own `memory trim|accept|restore`. The original in `~/.claude` was only read.
  - Call 1 (code as first built, ladder only): 415 ms, 27,539 input tokens, $0.0012, model `typesafe/jev-1.14-20261014`.
    Index 4.4k, proposal 4.1k estimated tokens (saves 324): still over, because Jev rated nearly every hook `needed` or
    `helpful` and the owner's hooks average 8 words, so the word cuts changed nothing.
  - Call 2 (with the last phase, whole hooks dropped one at a time): index 17,694 bytes (4.4k est.), proposal and accepted
    index 15,980 bytes (4.0k est., saves 429); sha256 of the backup equals the original's; `restore` gave the original's
    sha256 back; the index was unchanged by `trim`. Log: one line, role `memory-trim`, no memory text.
  - The phase code was then simplified (the drop order sorted by Jev's rating was dead, since the ladder had already
    dropped every redundant and helpful hook before it ran). The live numbers are from before that edit; a unit test
    asserts the behaviour of the simplified code, and no third Jev call was made.
- **Not reached by honest cuts:** 116 titles and file names are most of this index. Getting far below 4k needs entries
  merged, which the plan's "dropping or merging hooks only" leaves to Jev's text and Jev cannot write text (below).

## Choices where the plan was silent

1. **Jev cannot rewrite the index.** `check_reply` accepts probability, choice and score answers only. The trim is built
   as: one choice question per entry (`needed`/`helpful`/`redundant` for its hook text, 0.7 floor, unsure reads as
   `needed`), then a fixed ladder of cuts in code (`assemble`) that stops once the index fits. The `Trimmer` trait keeps
   the seam the plan's wording needs.
2. **Entries.** A line starting `- ` or `* ` that contains `](` is an entry; the lines that follow it and are not another
   entry, a heading or blank continue it. A hook holding a pointer of its own (`](` or `[[`) is never cut.
3. **The pointer check** compares the set of every `](target)` and `[[name]]` in the original with the proposal's. It runs
   at `propose` (refused and not written) and again at `accept`. A proposal must also be non-empty and smaller.
4. **Where a proposal and backups live:** `MEMORY.md.proposed` beside the index (the plan); backups at
   `<home>/nirvana/backup/memory/<folder_hash>-<yyyymmddThhmmssZ>-<nn>.md`. The counter is always present so two backups in
   one second sort in time order (found while writing the restore test: `-1.md` sorts before `.md`).
5. **`restore`** takes the newest backup for the folder and deletes a pending proposal. It does not back up the trimmed
   file first.
6. **`status` returns `Some` for any folder with an index**, over the limit or not; `over` says which.
7. **`discard`** returns `Ok(false)` when there is nothing to discard.
8. **Command exit codes:** a refusal or failure prints to stderr and exits 2 (the other `herdr` commands' usage code).
9. **The limit's home.** The plan names `trim_over_tokens` but no file. It is read from the top of P1's `preload.toml`,
   with an environment override for checks.
10. **What leaves the machine on a live call:** titles and the first 300 characters of each hook, secret shapes redacted.
    That is memory content sent to the Jev endpoint, the same posture as the other Jev calls; the owner may want a say.
11. **Batch size:** 120 entries per call; the wire has no tighter limit (116 went in one call).
12. **`CLAUDE_CONFIG_DIR`** is re-read in `nirvana_memory_trim` because `nirvana_claude::claude_config_dir` is private and
    that file is not mine; the six lines are copied.

## What this package does not do

- No hook was installed into a running Nirvana Claude, and `nirvana/install.py` was not run; the hooks arrive with the
  plugin at the next install.
- `nirvana window`'s `--resume` (P1) and the panel's `t`/`a`/`x` keys (P2) are not built here.
- No control for the `memory` dispatch arm in `main.rs`: a source scan is the hollow gate the memory names. The built
  binary was run instead (below).
