## What was built

1. **The rule, `src/nirvana_superpowers.rs`.** Pure functions: `family` (Opus, Sonnet, Other from an id, alias or
   label), `entries` (Opus: each id `false`; else none), `superpowers_ids` (names whose part before `@` is
   `superpowers`, sorted, once; the default when none), `installed_names` and `enabled_names` (keys only), `merged`
   (adds the entries under `enabledPlugins`, keeps every other key, refuses a non-object). File glue with every path a
   parameter: `ids_for`, `launch_settings_in`, `worker_settings_in`. `claude_dir()` is `None` in a test build, so no
   test reaches the owner's `~/.claude`.
2. **Nirvana Claude, `src/nirvana_launch.rs`.** `launch_args` is now `launch_args_in(..., claude_dir())`. After the
   seat and the preset are known, the one `--settings` value is replaced by
   `<home>/nirvana/launch/<folder hash>.opus.settings.json` on an Opus seat. Sonnet and others keep today's value and
   nothing is written. An error logs one `tracing::warn!` line and keeps today's argv. New Nirvana, Fresh Nirvana,
   the verb's space, a restored pane (`nirvana_relaunch.rs` through `nirvana_start_agent`) and Restart Claude all go
   through `launch_args`, each from its own seat.
3. **Claude workers, `src/nirvana_worker.rs`.** `worker_argv` (new) is what `seat exec` starts: `argv`, the folder's
   worker preset (`nirvana_preset::worker_settings_in`), then `worker_settings`, which on an Opus Claude worker returns
   `<home>/nirvana/launch/<cwd hash>.opus.worker.settings.json` (the preset merged with the entries, or the entries
   alone), and the preset otherwise. An error prints one line in the worker's view and keeps the preset.
   `with_preset_settings` is unchanged, so the argv still has at most one `--settings`.
4. `src/nirvana_preset.rs`: `worker_settings_for` removed. Its one caller now calls `worker_settings_in` with the
   same `nirvana_seat::dir()`, inside `worker_argv`, so the lookup is under test.

## Do workers load superpowers today?

No, as far as the records on this machine show. Every Claude worker stream found under `*/.nirvana/runs/*/streams/`
in `C:\Users\fahim\Desktop\Pojects` (19 streams, three projects, all `claude-sonnet-5-5`) has an `init` event whose
`plugins` are `cc-plugin-agents-md`, `cc-plugin-telemetry` and `cc-plugin-plugin-authoring` only, and whose `skills`
hold no `superpowers:` skill. The owner enables superpowers in user settings; `--setting-sources project` skips the
user layer, so its `enabledPlugins` never applies to a worker. No Opus worker stream exists to read, and the reading
is of past runs, not a new probe (no `claude` was run). The rule applies to workers anyway, since a `--settings` file
always applies: a project that enables superpowers in its own `.claude/settings.json` would load it in an Opus worker
without this rule.

## Discrepancies ("The plan was wrong here")

1. **One path for two bases.** §3 names `<home>/nirvana/launch/<folder hash>.<family>.settings.json` for Nirvana
   Claude and says workers do "the same". A worker's base is the worker preset (no `NIRVANA_ORCHESTRATOR=1`), so it
   cannot share Nirvana Claude's file for the same folder. Workers get `<folder hash>.<family>.worker.settings.json`,
   hashed by the worker's own folder (its worktree), the way the preset keeps `.settings.json` and
   `.worker.settings.json` apart.
2. **`<family>` is only ever `opus`.** The rule has no entry for Sonnet or any other model, so the launch passes
   today's file and nothing is written; a `.sonnet.` file would be a copy with nothing added.
3. **"Nirvana Claude starts on Opus medium by default"** holds when Balanced has no fresh readings. With fresh
   readings, Balanced's climb moves the orchestrator to Sonnet at climb 0.85 and above (`orchestrator_seat_balanced_at_t_0_5`),
   and the rule then leaves superpowers on, as the owner's L3 asks.
4. **The wiring lines that only run outside a test.** `launch_args` passing `claude_dir()` and `seat exec` calling
   `worker_argv` with `nirvana_seat::dir()` and `claude_dir()` have no control: in a test build `claude_dir()` is `None`
   by design, and `seat exec` starts a real CLI. Every decision behind them is under a control.
