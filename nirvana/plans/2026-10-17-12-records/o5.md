## What the live and scripted runs found, and what changed

1. **The gate committed build output.** O3's workers do not commit, so the gate commits their work before the rebase;
   the first version took every untracked file, `mul`'s `__pycache__` included, and then failed `mul` on the owned
   axis for its own commit. The commit now takes a new file only when an `owns:` pattern names it, and says what it
   left out (`sub`'s gate above).
2. **A passed order could never merge after another merge.** `gate merge` refuses trees that moved, and `gate run` on
   a passed order returned the old pass. A passed order whose branch or integration tip moved is gated again.
3. **unittest's `FAILED (errors=2)` read as a case.** The held-out base run counted 4 cases of 3.
4. **The retro merged three gaps into one.** The send-back sentences of the rebase, owned and tests gaps share a
   template and score 0.63, 0.61 and 0.57 to each other; at 0.6 they were one gap, and one row per (gap, run) kept
   only the first. Gaps are now compared only within one kind and gate axis, on their cause.

## Choices where the plan was silent

1. **The gate lines** are lines that start with `owns:`, `test:`, `check:` or `serves:`, anywhere in the order, any
   number of times. They are read from the chain's root order, so a send-back keeps them; herdr's footer and the
   send-back brief start no line with one of the four words. `owns:` patterns: `*` and `?` within a name, `**` across
   folders, `/` the separator.
2. **The integration branch** is `nirvana-integrate/<run>`, made from the project's HEAD the first time an order of
   the run is gated, and never checked out: `gate merge` is `commit-tree` (two parents and the head's tree, since the
   head is rebased onto the tip) and a compare-and-swap `update-ref`. Not under `nirvana/`: O3's order branches are
   `nirvana/<order>`, and git cannot hold `nirvana/x` beside `nirvana/x/...`.
3. **The gate commits the worker's work** on its branch before the rebase ("herdr gate: the work of <order>", with a
   `Nirvana-Order` trailer), since a rebase cannot carry a dirty tree. Tracked changes always; a new file only when an
   `owns:` pattern names it, or every new file when the order names none; herdr's `.nirvana/` never.
4. **A `blocked` Work Report fails the report axis** and is sent back; a `needs_answer` worker is `asked` by O3 and
   the gate refuses to rule on it.
5. **No `owns:` line** is a note listing the changed files, never a block (old Nirvana, decision 0016 §8.8 point 4).
   **No `test:` line** is a note, unless the order names `check:`s, which then fail for want of a command.
6. **Feature-size** (§7.3 names it with no rule) is a `build.*` or `fix.debug` class at size medium or large.
   **Load-bearing** is the class's `blast` in `seats.toml`: plan and build.load_bearing today.
7. **The reviewer and the author are booked by the gate and started by the orchestrator** with the printed `herdr seat
   run` line, which O3 honours through the booking. A reviewer runs in the project's folder, not a worktree, so its
   print-mode file tools reach the order's worktree under `.nirvana/worktrees/`; its order says to change nothing,
   an instruction, not a sandbox. Its verdict is its Work Report's status: `done` approves, `blocked` sends back with
   its `gotchas`, `needs_answer` waits.
8. **The held-out check's shape**: the author writes `.nirvana/heldout/` and a one-line `COMMAND` with `{dir}`; the
   gate copies the folder to `<run>/heldout/<order>/` beside the journal, deletes it from the author's folder, refuses
   an author that changed a repository file, and runs `COMMAND` there at the base. Cases are read from pytest `-rA`
   and `-v`, cargo test and unittest `-v`. The builder's worktree never holds the check.
9. **The gate's own record**, `<run>/gate/<order>.json` beside the journal: an order's reviewers and authors, the
   captured check, the last five axes with the trees they ran at (so a returning review reruns nothing on the same
   trees). The journal still carries every ruling with all its axes.
10. **A send-back seats and starts its child at once**, on the seat the rule picks for the order's class, in the
    parent's worktree (R6: in a run, "seat, gate and send back without asking"). The child is `<root>-s<n>`; the cap
    counts send-backs along the chain to its root.
11. **The outcome words**: pass, sent_back, failed, asked, reseated. The tally counts pass as a pass, reseated not at
    all, every other word (O2's "sent back" included) as a failure. A hypothesis.
12. **Retro gap kinds** beyond the brief's list: the send-back cap spent and a crash loop, both outcome-tagged misses
    with a named cause, and a worker that failed with its reason (outcome-tagged). Without them no gap could graduate
    on one miss.
13. **Retro targets**: the Nirvana Claude plugin's `skills/` and `agents/`, or a `seats.toml:seat.<id>.use.<effort>`
    cell; everything else is refused, the gate's skill and any `decisions/` path by name. A proposal's text is a
    template per gap kind; a rate-limit or re-seat gap proposes the cell with the record's measured mean use.
14. **A refusal stays by meaning, not only by key**: a gap as alike as 0.6 to a refused gap is refused too, so a gap
    said a new way cannot slip past.
15. **`herdr run retro propose --json`** takes the orchestrator's own proposal under the same scope and quote checks.
16. **A lesson's description is its name** (the Work Report's `lesson` has no description); its slug is the name in
    lowercase letters, digits and dashes. A lesson of the same name replaces the older text and keeps its counters.
17. **The decay rule**: in the briefs for its first 6 offers, then only while `passed_after_opened × 3 ≥ offered`; both
    numbers hypotheses. "Opened" is a tool call whose input names the lesson's file; the order file read back names
    every offered lesson, so a tool result does not count.
18. **The NIRVANA.md line** O4b's digest reads, one per project, replaced in place: `- lessons for <root>: <n> live in
    <root>\.nirvana\lessons; \`herdr lessons for --class <class>\` lists a class's <!-- herdr-lessons <root> -->`. O4b
    was not built when this was, so the line is this package's choice for O4b to read.
19. **Locks**: one gate at a time per project (`.nirvana/runs/.gate.lock`), and the lessons index under
    `.nirvana/runs/.lessons.lock`; both under `runs/`, which O3's `.gitignore` ignores.

## Not measured

- A real reviewer or held-out author: both ran only as hand-written deliveries. Whether argon writes a check that is
  valid at the base, and whether a review's `blocked` gotchas make a useful brief, are unmeasured.
- The served axis on a real ops worker. A worker runs in a kill-on-close job object (O3), so a server started from
  its own shell dies with it; the gate's skill names `herdr pane run "$HERDR_PANE_ID" "<cmd>"` as the way a server
  outlives the worker, and that was not run. The axis was checked on recorded process and listener tables only.
- The send-back cap reached live: the cap and the `asked` ruling are unit-tested; no order was sent back three times.
- A worker that games a named check by printing its name: the check is a substring of the filtered output, so a
  worker that prints `test_sub` would pass `sub`. Not seen; the order's `test:` command is the gate's, but its output
  is the worker's code's.
- A lesson's `class` is not checked against `seats.toml` (flash's `git-rebase`); such a lesson is never offered.
- An order run in the project's folder, not a worktree: the owned axis then reads the project's uncommitted files,
  the owner's included.
- Off Windows nothing was built: the served axis reads no table there.
