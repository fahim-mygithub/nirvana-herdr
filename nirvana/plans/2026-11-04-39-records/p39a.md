## What was built

- `src/nirvana_remote.rs`: the supervisor. Inside the default herdr server only (`skip_reason`: not when
  `HERDR_SOCKET_PATH`, `XDG_CONFIG_HOME` or a named session is set, or `NIRVANA_REMOTE=off`). Every 60 s it reads
  `tailscale status --json`. When Tailscale is running and the tailnet has HTTPS on, it binds `127.0.0.1:7790` and runs
  `tailscale serve --bg --yes --https=8443 http://127.0.0.1:7790` once. It writes `<herdr data dir>/nirvana-remote.json`
  (up with its URL, or off with why) on every check. On stop it runs `tailscale serve --yes --https=8443 off` and
  removes the file. A failed serve closes the listener again. A taken port means no serve.
- `src/nirvana_remote/http.rs`: an HTTP/1.1 server on tokio built on `httparse`. One request per connection, a
  16 KiB head limit, a 10 s read timeout, 32 connections at once, GET and HEAD only.
- `src/nirvana_remote/peer.rs`: the check on each connection. The owning pid of the caller's end comes from
  `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_CONNECTIONS)` and must be the Tailscale service's pid
  (`QueryServiceStatusEx`) or a `tailscaled.exe` child of it. This is checked before a byte of the request is read.
- `src/nirvana_remote/routes.rs`: the identity rule. The request needs exactly one `Tailscale-User-Login`, and it must
  equal the login of the user this PC is signed in to Tailscale as. A tagged device, Funnel traffic, a share
  recipient, no header, or two headers each get a 403 and a `warn!` in herdr-server.log. Routes: `/`, `/app.css`,
  `/app.js`, `/pcs.js`, `/api/hello`, `/api/pcs`.
- `src/nirvana_remote/pcs.rs`: the PC list. This PC comes first, then the owner's other machines. Phones, tagged
  machines and other users' machines are left out. Online peers are probed in parallel at
  `https://<dns>:8443/api/hello`, 2 s each. The states are Nirvana ("3 spaces, 2 agents at work"), online ("Online,
  Nirvana not running") and asleep ("Asleep, last seen 2 h ago").
- `src/nirvana_remote/herdr.rs`: the socket API, called in process over the same `ApiRequestMessage` channel the socket
  server uses (`workspace.list`, `agent.list`).
- `src/nirvana_remote/tailscale.rs`: the `Tailscale` trait, the status parser, the `Off` reasons, and the CLI runner.
  The runner has no stdin and no console, sets `BROWSER` to a no-op (CLAUDE.md rule 15), and kills the child at 15 s.
- `src/nirvana_remote/page/`: the page shell (`index.html`, `app.css`, `app.js`) and screen 1 (`pcs.js`), embedded with
  `include_str!`. It takes the prototype's colours, Inter and JetBrains Mono, the press, entry and pulse motion, its
  copy, and its reduced-motion rule word for word.
- The servers block in the sidebar foot (`src/client/shell/nirvana_footer.rs`, `sidebar.rs`) leads with a `remote`
  row: `● remote :8443` in green when up, `○ remote HTTPS off` with the reason in yellow when off. The row is read from
  the state file at most every 3 s. A file older than 150 s reads as gone. The block shows for this row alone when no
  space runs a server.
- Wiring: `src/server/headless/bootstrap.rs` starts the supervisor after the server is ready and awaits its stop after
  `server.run()`. `src/main.rs` declares the module. Cargo changes: the `httparse` crate, tokio `net`, time `parsing`,
  and windows-sys `Win32_System_Services`. Cargo.lock adds one package, httparse 1.10.1.

## The login route: (a), `tailscale serve`, with the caller's process checked

**Choice.** (a): Tailscale terminates HTTPS and renews the certificate, and Nirvana Remote listens on 127.0.0.1 only.
(b) would have added a TLS server (rustls server side, a reload every 90 days for the Let's Encrypt certificate) and a
`whois` process per connection, and it has the same local hole as (a) (below).

**The plan's trust argument does not hold as written.** The plan says a local process "can already drive the herdr
socket, so it adds no new door". Measured: herdr's pipe on Windows is created with SDDL `D:P(A;;GA;;;SY)(A;;GA;;;OW)`
(`src/platform/windows.rs:44`). That admits SYSTEM and the owner only. A 127.0.0.1 TCP port admits any process of any
Windows account. That includes a browser page through DNS rebinding, since the attacker's origin can then set custom
headers. Under (a) alone, any local process could send `Tailscale-User-Login: <owner>` and drive every agent. That
would be a new door. Route (b) has the same hole: a local process that connects to the PC's own 100.x address is
`whois`-named as the owner's node and user.

**The fix, which gives the trust argument.** Headers are read only from a connection whose owning process is the
Tailscale service, or a `tailscaled.exe` child of the service. A non-admin cannot start a process under a
LocalSystem service, and cannot forge a parent through PROC_THREAD_ATTRIBUTE_PARENT_PROCESS without a
PROCESS_CREATE_PROCESS handle to the service. So the check is at least as tight as the pipe's ACL. Tailscale strips
any `Tailscale-User-*` header the caller sends and sets its own (KB 1312: "it will remove them for security reasons,
to avoid header spoofing"). It sets none for tagged devices or Funnel, so both get a 403 here. A user a device was
shared with gets their own login and also gets a 403.

**Measured 2026-11-04 (read-only commands only):**
- `tailscale version`: 1.102.2.
- `status --json`: `BackendState` is Running and `CertDomains` is `null`, so HTTPS is off (owner step 1).
  `User[Self.UserID].LoginName` exists. There are 4 peers, all the owner's and all offline; one is iOS.
- `tailscale serve status`: "No serve config". Nothing of the owner's sits on 8443.
- `whois --json <own ip>`: has `Node` and `UserProfile.LoginName`.
- `sc queryex Tailscale`: RUNNING, PID 6716. A non-admin can query it.
- Win32_Process: a second `tailscaled.exe` (8672) runs with parent 6716. Neither image path is readable without
  admin. That is why the check uses the service pid and the parent link, not the path.
- The connection lookup was checked on this PC by `a_connection_owner_is_the_process_that_opened_it`: the row found
  is the test's own pid, and `peer::System` refuses it with that pid named.

**Not measured, so a hypothesis:** that tailscaled's serve proxy dials 127.0.0.1 from 6716 or 8672. If it dials from
somewhere else, every request gets a 403, and the log names the pid and image (`pid N (name), not the Tailscale
service`). It fails closed. The owner's first live sign-in settles it.

## The HTTP server: httparse on the tokio already here

hyper 1 with hyper-util would add 8 crates. axum adds more. tiny_http runs its own threads, not on tokio. httparse is
hyper's own parser: no dependencies, fuzzed, and already in the cargo cache (no download). The server around it is
about 150 lines. It needed tokio's `net` feature, which is a feature of a crate already present.

## How a screen is added (P39b-e)

1. Write `src/nirvana_remote/page/<screen>.js`:
   `Nirvana.screen('<name>', { render(el, params, nv) { ... } })`. Build the DOM with `nv.h(tag, {class, text,
   onclick, ...}, ...children)` and `nv.icon(name, size, stroke)`. Never use `innerHTML`, because names come from
   Tailscale and herdr. Fetch with `nv.getJson(path)`. Move with `nv.go('<name>', 'r'|'l'|'f', params)`: right goes
   deeper, left goes back, f fades. Each move is a history entry, so the phone's back gesture works.
2. Add its row to `routes::ASSETS` and a `<script src="/<screen>.js">` to `index.html` after `pcs.js`. The CSP allows
   no inline script.
3. Its API routes go in `Site::handle`'s `match`. The identity check already runs before every route. A route that
   takes a body (uploads) needs `http.rs` to read one up to its `Content-Length`. It reads none today.
4. The CSS goes in `app.css` or a stylesheet of its own, added the same way.

Screen 1 already calls `nv.go('spaces', 'r', {pc})` once `nv.has('spaces')`. Until then a tap on this PC says "This
PC's spaces open here in the next release." Another PC's Nirvana row links to that PC's own page.

## Where the plan was wrong or open

1. §1.2's "adds no new door" is wrong for a 127.0.0.1 port; the measurement and the fix are above.
2. "The Servers square row": there is no Servers square. The servers live in the sidebar foot's "servers" block, and
   the row is there.
3. The serve uses HTTPS port 8443, not 443, so it cannot clobber anything the owner serves on 443. The phone's URL is
   `https://<pc>.<tailnet>.ts.net:8443/`.
4. Fonts load from Google Fonts, as in the prototype. "Embedded, no installs" holds for the page itself; offline the
   page falls back to system-ui.

## Owner steps for the live check, in order

1. In the Tailscale admin console, turn on MagicDNS and HTTPS Certificates (DNS page). Afterwards `tailscale status
   --json` shows `CertDomains`.
2. Merge and install this build, then restart Nirvana-Herdr. The sidebar should show `● remote :8443`. If it shows
   `○ remote <why>`, the reason is in `nirvana-remote.json` and herdr-server.log.
3. On Windows, `tailscale serve` may need the Tailscale operator right. If the row says "serve failed", run once:
   `tailscale serve --bg --https=8443 http://127.0.0.1:7790`.
4. Install Tailscale on the phone and sign in with the same account.
5. Open `https://quadstation-w11.<tailnet>.ts.net:8443/` on the phone. It should show "Your PCs" with this PC first.
   If you get a 403, read herdr-server.log for `nirvana remote refused`: it names the pid that dialed, which settles
   the dialer hypothesis above.

## Not done, or unsure

- No live run against real Tailscale. Every Tailscale path is fake-tested.
- Which tailscaled process dials the backend is not measured (above).
- The supervisor's start and stop inside `run_server` has no test, since that needs a real server.
- A server killed hard leaves the serve config pointing at a dead port. The phone then gets a 502 until the next start
  sets it again.
- The page's motion and JS are checked by reading the served text and by one headless measurement, not by a JS test
  suite. Source-scanning assertions are weak (memory `source-scanning-gates-are-hollow`).
- Non-Windows: Nirvana Remote reports "Windows only" and does not serve.
