## The login route: (a), `tailscale serve`, with the caller's process checked

**Choice.** (a): Tailscale terminates HTTPS and renews the certificate, and Nirvana Remote listens on 127.0.0.1 only.
(b) would have added a TLS server (rustls server side, a reload every 90 days for the Let's Encrypt certificate) and a
`whois` process per connection, and it has the same local hole as (a) (below).

**The plan's trust argument does not hold as written.** The plan says a local process "can already drive the herdr
socket, so it adds no new door". Measured: herdr's pipe on Windows is created with SDDL `D:P(A;;GA;;;SY)(A;;GA;;;OW)`
(`src/platform/windows.rs:44`). That admits SYSTEM and the owner only. A 127.0.0.1 TCP port admits any process of any
Windows account. That includes a browser page through DNS rebinding, since the attacker's origin can then set custom
headers. Under (a) alone, any local process could send `Tailscale-User-Login: <owner>` and drive every agent. That
would be a new door. Route (b) has the same hole: a local process that connects to the PC's own 100.x address is
`whois`-named as the owner's node and user.

**The fix, which gives the trust argument.** Headers are read only from a connection whose owning process is the
Tailscale service, or a `tailscaled.exe` child of the service. A non-admin cannot start a process under a
LocalSystem service, and cannot forge a parent through PROC_THREAD_ATTRIBUTE_PARENT_PROCESS without a
PROCESS_CREATE_PROCESS handle to the service. So a direct dial of 127.0.0.1:7790 is refused whatever its account.
*Corrected in the review round (S1):* this is not "at least as tight as the pipe's ACL", because tailscaled also
serves the mount on this PC's own Tailscale address; see "Review round", S1. Tailscale strips
any `Tailscale-User-*` header the caller sends and sets its own (KB 1312: "it will remove them for security reasons,
to avoid header spoofing"). It sets none for tagged devices or Funnel, so both get a 403 here. A user a device was
shared with gets their own login and also gets a 403.

**Measured 2026-11-04 (read-only commands only):**
- `tailscale version`: 1.102.2.
- `status --json`: `BackendState` is Running and `CertDomains` is `null`, so HTTPS is off. *Stale:* the owner turned
  HTTPS on for the tailnet on 2026-11-04 after this build; see "Review round", measurements.
  `User[Self.UserID].LoginName` exists. There are 4 peers, all the owner's and all offline; one is iOS.
- `tailscale serve status`: "No serve config". Nothing of the owner's sits on 8443.
- `whois --json <own ip>`: has `Node` and `UserProfile.LoginName`.
- `sc queryex Tailscale`: RUNNING, PID 6716. A non-admin can query it.
- Win32_Process: a second `tailscaled.exe` (8672) runs with parent 6716. Neither image path is readable without
  admin. That is why the check uses the service pid and the parent link, not the path.
- The connection lookup was checked on this PC by `a_connection_owner_is_the_process_that_opened_it`: the row found
  is the test's own pid, and `peer::System` refuses it with that pid named.

**Not measured, so a hypothesis:** that tailscaled's serve proxy dials 127.0.0.1 from 6716 or 8672. If it dials from
somewhere else, every request gets a 403, and the log names the pid and image (`pid N (name), not the Tailscale
service`). It fails closed. The owner's first live sign-in settles it.

## How a screen is added (P39b-e)

1. Write `src/nirvana_remote/page/<screen>.js`:
   `Nirvana.screen('<name>', { render(el, params, nv) { ... } })`. Build the DOM with `nv.h(tag, {class, text,
   onclick, ...}, ...children)` and `nv.icon(name, size, stroke)`. Never use `innerHTML`, because names come from
   Tailscale and herdr. Fetch with `nv.getJson(path)`. Move with `nv.go('<name>', 'r'|'l'|'f', params)`: right goes
   deeper, left goes back, f fades. Each move is a history entry, so the phone's back gesture works.
2. Add its row to `routes::ASSETS` and a `<script src="/<screen>.js">` to `index.html` after `pcs.js`. The CSP allows
   no inline script.
3. Its API routes go in `Site::handle`'s `match`. The identity check already runs before every route. A route that
   takes a body (uploads) needs `http.rs` to read one up to its `Content-Length`. It reads none today.
4. The CSS goes in `app.css` or a stylesheet of its own, added the same way.

Screen 1 already calls `nv.go('spaces', 'r', {pc})` once `nv.has('spaces')`. Until then a tap on this PC says "This
PC's spaces open here in the next release." Another PC's Nirvana row links to that PC's own page.

## Review round (2026-11-04, "Opus high - P39a review round")

The review is `p39a-review.md` on 558541f3. The principle the round works to: Nirvana Remote changes only the serve
mount it made, never leaves a trusted origin pointing at a port anyone could take, and says "up" only when it has
checked that it is.

### The mount is a foreground serve (B2, S2, S3)

The build ran `tailscale serve --bg --yes --https=8443 http://127.0.0.1:7790` and, at stop, `serve --yes --https=8443
off`. A `--bg` mount lives in tailscaled's state, so it outlives herdr: after a hard kill, a crash or a reboot it
pointed `https://<pc>.<tailnet>.ts.net:8443/` at a free 7790, and any local process could bind 7790 and serve its own
script under the owner's trusted origin. `--yes` also meant a blind overwrite, and `off` at stop removed whatever was
on 8443.

Now Nirvana Remote holds a **foreground** serve: a child `tailscale serve --https=8443 http://127.0.0.1:7790`, no
`--bg`, no `--yes` (`tailscale::hold_args`), for as long as it serves. I read why that holds in Tailscale 1.102.2's
source (`ipn/serve.go`, `ipn/ipnlocal/serve.go`, `ipn/ipnlocal/local.go`, `cmd/tailscale/cli/serve_v2.go`, tag
v1.102.2, read only):
- A foreground config is keyed by the CLI's IPN bus session. `WatchNotifications` ends with
  `defer b.DeleteForegroundSession(sessionID)`, so the mount is deleted when the CLI process ends, cleanly or not.
- On reload from disk (a tailscaled restart, a reboot) `reloadServeConfigLocked` drops every foreground session that
  no watcher holds ("remove inactive sessions"). So no reboot leaves it behind.
- `setServeConfigLocked`'s check: "New foreground config cannot override existing listeners--neither existing
  foreground listeners nor existing background listeners" ("listener already exists for port"). So tailscaled itself
  refuses to put Nirvana Remote over anything on 8443, even in a race after Nirvana's own look.
- The child is in an unnamed job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`tailscale.rs` `job`). Windows closes the
  job's one handle when herdr ends, a hard kill included, which kills the CLI, which ends the session. If the job
  cannot be made, the CLI is killed and the serve fails: a mount that could outlive herdr is not started.

Before serving, `bring_up` reads `tailscale serve status --json` and classifies 8443 (`tailscale::mount`):
- **Free**: serve.
- **Ours**, recognised as exactly one `"/"` handler under `<this pc's dns>:8443` whose `Proxy` is
  `http://127.0.0.1:<the local port>` (trailing `/` ignored), HTTPS, no `TCPForward`, no `AllowFunnel`. Anything more
  on the port (a second handler, another host name on 8443, Funnel, a TCP forward) is **Other**.
  - In a foreground session: another live Nirvana Remote holds it. Report "8443 taken", touch nothing.
  - In the background config: a stale mount (the P39a build's `--bg`, or the old owner step 3 typed by hand). It is
    cleared with `tailscale serve --https=8443 off` (no `--yes`: with one handler the CLI asks nothing) **before** the
    port is bound, so it goes even when a squatter holds 7790; the row then says "port 7790 busy".
- **Other**: report "8443 taken" with what is there, and change nothing.

Then it binds 7790, starts the child and counts the serve as up only once `serve status` shows the foreground mount
(10 s, `Config::confirm`). At stop, and when a mount is found gone, the child is ended first and the port is held
until `serve status` no longer shows the mount (at most 3 s, `GONE_WAIT`), then the listener closes. There is no
`serve_off` any more: the only thing Nirvana Remote removes is a background mount that is exactly its own.

Each 60 s check while serving (S3) asks whether the child still runs and whether `serve status` still shows the
mount. If either fails, the row goes off as `serve gone` with the reason in the state file, everything is torn down,
and the next check sets it again (`a_mount_that_goes_away_turns_the_row_off_and_is_set_again`). I chose a full
teardown over the review's "rerun serve_on and keep the listener": the child's end is itself the signal, and the next
check is the same path as a first start.

**Unix socket or named pipe?** `tailscale serve --help` on this PC: "On Unix-like systems, you can also specify a Unix
domain socket ... (Linux/macOS/BSD only)". No named pipe target exists. The proxy code has no GOOS check for `unix:`,
and Windows has AF_UNIX, but it is documented as not supported, tokio has no Windows `UnixListener`, and a socket file
in a writable folder can be re-created by another process anyway. Not taken.

**The window that remains.** Between herdr's death and tailscaled deleting the session: Windows closes herdr's
listening socket and its job handle in the same teardown, the job kills the CLI, and tailscaled sees its bus
connection close. A process that binds 7790 inside that gap (expected milliseconds; not measured) would receive
requests until the deletion, with none of Nirvana Remote's checks in the way: in that gap a squatter would get the
owner's phone's requests, identity headers and all. The live check below measures how long the mount
survives a hard kill. Also: tailscaled itself crashing while herdr runs ends the CLI; the mount is gone with it.

### Who is let in (S1, S5)

**S1, the review's claim was right, and its "no cheap code fix" was wrong.** Read in the same source:
`localListener` ("host-level net.Listen for a specific (Tailscale IP, port)") means tailscaled serves its serve ports
on this PC's own Tailscale address, so a local process of any Windows account reaches the mount through tailscaled,
which whois-names the source (this PC, the owner's user) and sets `Tailscale-User-Login: <owner>`. The review said
"serve adds no source-address header". It does: `addProxyForwardedHeaders` sets
`X-Forwarded-For = SrcAddr.Addr()` with `Header.Set`, replacing anything the caller sent. So `routes::from_another_device`
now requires exactly one `X-Forwarded-For`, inside Tailscale's ranges (100.64.0.0/10 or fd7a:115c:a1e0::/48), and not
one of this PC's own `TailscaleIPs`. A local process cannot bind another device's tailnet address as its source; a
source outside the ranges (a LAN or loopback address) gets no Tailscale identity in the first place.

This is code against a hypothesis about real traffic, not a measurement. Until the live check shows a local request
refused with "this PC's own Tailscale address", the claim stands at **"as tight as any process of the owner's Windows
account"** (true on this single-user PC; on a PC with a second account it would be "any process of any account").
`peer.rs`'s header and `Report::up`'s long text ("serving <url> to this PC's Tailscale login only", N6) say no more.

**S5.** For every request: the `Host` must be exactly `<this pc's dns>:8443` (case-insensitive), else 421
(`for_this_pc`); tailscaled passes the caller's Host through (`r.Out.Host = r.In.Host`). For anything but GET and
HEAD (`same_site`): a request with neither `Sec-Fetch-Site` nor `Origin` is refused; `Sec-Fetch-Site`, when sent, must
be `same-origin` or `none`; `Origin`, when sent, must be exactly `https://<this pc's dns>:8443`. Every route is still
GET; the check runs before the 405, so P39b's POST routes inherit it.

### The rest

- **B1.** `skip_reason` takes `debug_build` (`cfg!(debug_assertions)` at the call): a debug build hosts it only with
  `NIRVANA_REMOTE=on`, and `on` does not lift the other gates. Since 0.55.1 that holds for the `nirvana` session's
  server too; "the other gates" no longer include `nirvana` as a named session (below). Checked:
  `src/config/io.rs:24` names `herdr-dev` for debug builds and sets neither variable, as the review said.
- **S4.** A refused connection or request logs at most once per key per 60 s (`routes::Throttle`; key = the pid, or
  the login and reason), the next line saying how many were held back; the map is capped at 1024 keys. The process
  snapshot is reused for 1 s (`peer::Snapshot`), but only to refuse: a caller the cached snapshot reads as the
  Tailscale service is read again from a fresh one before it is trusted, so a reused pid is never let in on old data.
  The TCP table and the service pid are still read per connection.
- **S6.** Tests for the 408 (with `http::Limits` so it takes 0.3 s), the 33rd connection waiting for a slot (the real
  32), the four headers on 200, 404, an identity 403 and a connection 403, and HEAD on each asset keeping its length.
  N7: every answer now carries the CSP, a refused connection's included.
- **S7.** The state file has the writer's `pid`. The server holding the port always writes it; any other writes only
  into a missing, stale or own-pid file, and removes it at stop only when it is its own.
- **N1.** `http::finish`: answer, close the sending half, then read and drop up to 64 KiB for up to 1 s. The first
  test (body sent with the head) stayed green with the drain sabotaged: hollow, so it was rewritten to send the body
  after the answer; that one goes red without the drain.
- **N2.** `/api/pcs` reuses one `tailscale status` for 5 s. **N3.** `%ProgramFiles%\Tailscale\tailscale.exe` when it
  exists (it does here: `C:\Program Files\Tailscale\tailscale.exe`), else PATH.

## Session fix (0.55.1)

Work order P39a-session, branch `p39a-session` from e906b27a (master, alpha 0.55.0), by "Opus high - P39a session
fix".

### The incident (measured 2026-11-04 on the owner's PC, after installing 0.55.0)

- The owner's window: `herdr.exe --session nirvana nirvana window "...3D-Printer Flow"`; its server
  `herdr.exe server` (child). Nirvana always launches as session `nirvana`: `src/nirvana_launch.rs:53`
  `pub const SESSION: &str = "nirvana";`, used at `:727`.
- `%APPDATA%\herdr\sessions\nirvana\herdr-server.log`:
  `INFO herdr::nirvana_remote: nirvana remote not started why="a named session's server"`.
- `tailscale serve status --json` → `{}`. The phone cannot reach anything.
- Cause: `skip_reason` skipped every named session, so it skipped the only server it exists for. The tests pinned
  "default hosts, `work` skips", never `nirvana`.

### The fix

- `skip_reason` skips a named session only when it is not `crate::nirvana_launch::SESSION`. The other rules keep
  their order: `NIRVANA_REMOTE=off`, `HERDR_SOCKET_PATH`, `XDG_CONFIG_HOME`, then the session, then the debug build.
  So a `nirvana` server under a test's socket or config, with `off`, or in a debug build without `on`, still skips.
  The match is exact: `Nirvana` and `nirvana-2` skip (`active_name` keeps the name as typed).

### The rest of the path, checked

- **The server gets the session.** `herdr --session nirvana` sets `HERDR_SESSION=nirvana` in the window process
  (`src/session.rs:484-493`, `apply_explicit_name`). The server is spawned from it with `server` and the inherited
  environment (`src/server/autodetect.rs:225-251`, which removes only the socket overrides). The server's
  `active_name()` (`src/session.rs:98-103`) reads `nirvana`. The incident's log path, `sessions\nirvana\`, agrees.
- **State file, writer and reader agree.** The server writes `state_path()`, which is `session::data_dir()` plus
  `nirvana-remote.json` (`src/nirvana_remote.rs`, `state_path`, passed into `Config` in `start`). The sidebar row
  reads the same `state_path()` (`foot_row`, called from `src/client/shell/sidebar.rs:557`) in the window's client,
  which has the same `HERDR_SESSION`. `data_dir()` is `data_dir_for(active_name())` (`src/session.rs:159-169`), so
  both are `%APPDATA%\herdr\sessions\nirvana\nirvana-remote.json`. Fine, no change.
- **Nothing else assumes the default session.** `src/nirvana_remote/*.rs` has no other `data_dir`, `config_dir`,
  socket path or session name: `herdr.rs` talks to the app over the in-process `api_tx`
  (`src/server/headless/bootstrap.rs:99`), not a socket path; `tailscale.rs`, `pcs.rs`, `peer.rs`, `routes.rs` and
  `http.rs` have no session at all. `bootstrap.rs` starts it for whichever server runs. The footer
  (`src/client/shell/nirvana_footer.rs:234,267`) only draws the row it is handed. Fine, no change.

### Two servers (the default session's and the `nirvana` session's)

Both may now host it. They do not share a state file: each writes its own session's data dir, so each window shows
its own server's row, and the S7 single-owner rule (`may_write`) only orders writers within one session. On one PC
they share port 7790 and the node's serve config on 8443. In `bring_up`, in this order:

1. `serve status` is read first. The first server's mount is a foreground session proxying `/` to
   `http://127.0.0.1:7790`, which the second reads as `Mount::OursForeground` (both use `LOCAL_PORT`), and returns
   `Off::ServeTaken("8443 is held by another running Nirvana Remote")` before it binds or holds anything. Its row:
   `○ remote 8443 taken`, long text "not serving, and nothing changed: ...".
2. If both look before either mounts, only one binds `127.0.0.1:7790`; the other gets `Off::PortInUse`
   (`○ remote port 7790 busy`) and returns before any hold.
3. Nothing in the second's path changes the first's mount: `clear_background` runs only for a `--bg` mount, which
   no 0.55 build makes; the second never holds, so its stop drops no hold.
4. Each check repeats this every 60 s, so when the first server stops, the second takes over within a check.

New test `a_second_sessions_server_finds_8443_taken_and_leaves_the_first_alone`: two supervisors on one fake
Tailscale, one fixed port, two state files. The first is up; the second reports `8443 taken` in its own file; the
first's mount, row and listener stand through the second's check and stop; one hold in all. Control
`p39a_second_session_taken` (a live foreground mount read as free) reddens it: the second then tries the port and
reports `port <n> busy`.
