  message), and `Vapid` (this PC's ECDSA P-256 key, an ES256 JWT, the `vapid t=..., k=...` header of RFC 8292 §3).
- `src/nirvana_remote/alerts.rs`: the endpoint allow-list (`endpoint`, `PUSH_HOSTS`), the phone's keys (`keys`), the
  change rule (`changes`), the push body (`payload`), the flap rule (`Debounce`), the store (`Alerts`: the key file,

  `GET /api/alerts`, `POST /api/alerts/subscribe`, `POST /api/alerts/unsubscribe`, and the home-screen app's files
  (`FILES`).
- `src/nirvana_remote/page/`: `sw.js` (the service worker), `manifest.webmanifest`, `alerts.js` (the switch on screen
  2), `icon-180.png` (served as `/apple-touch-icon.png`), `icon-192.png`, `icon-512.png`. `index.html` gains the

- Wiring: `routes.rs` (`Site::alerts`, one dispatch right after P39d's, so after every check), `nirvana_remote.rs`

- Tests: `src/nirvana_remote/tests_alerts.rs` (17). Controls: `nirvana/controls.d/p39e.py` (44).

## The crypto: ring, already in the tree

ring 0.17.14 is compiled into herdr today for TLS (rustls under ureq, `Cargo.lock`), and it has every primitive the
two RFCs use: `agreement::ECDH_P256` with an ephemeral key, `hkdf::HKDF_SHA256`, `aead::AES_128_GCM`, and
`signature::ECDSA_P256_SHA256_FIXED_SIGNING` (the fixed `r || s` an ES256 JWT carries). It is added with
`default-features = false`, the features it already has. The alternatives: the `web-push` crate brings its own HTTP
client and an `ece`/OpenSSL backend; `p256` + `hkdf` + `aes-gcm` from RustCrypto are about a dozen packages new to the
lock. The scheme over ring is about 100 lines and reproduces RFC 8291 Appendix A byte for byte
(`rfc_8291_appendix_a_is_reproduced`: CEK, NONCE, the 86-octet header and the ciphertext). ring cannot import an
ECDH private key, so the vector is checked from its `ecdh_secret` on; the ECDH step itself is checked by a round
trip in which the test plays the phone (its own one-shot key, the header's key id, the record opened, the delimiter
checked).

`url` (2.5.8, under ureq) parses the endpoint once; the parsed URL is what is stored and POSTed to, so the check and
ureq read the same URL.

- **Service worker** `/sw.js`, scope `/`: **it caches nothing, and has no fetch handler at all.** Every request goes

  'self'`. Nothing new is allowed, no inline script or style, and the worker script answers with the same CSP as
  every response. A test reads the CSP on the manifest's answer.
- All six files are served behind every check (P39a/P39b), from `alerts_routes`; a POST to one is 405.

## Alerts (items 2-3)

- **The switch** (`alerts.js`), below the spaces on screen 2. The prototype draws the notification (screen 7), not a
  switch; this one is drawn in Nirvana Dark's tokens (`--card`, `--teal-deep`, `--sleep`). On a tap:
  `Notification.requestPermission()` is the first call in the click handler, before anything is awaited (iOS asks
  only inside a user gesture); then `GET /api/alerts` (the PC's public key), `pushManager.subscribe({userVisibleOnly:
  true, applicationServerKey})` (re-subscribing when an old subscription has another key), and `POST
  /api/alerts/subscribe` with `subscription.toJSON()`. Off: `POST /api/alerts/unsubscribe` and `unsubscribe()`. On
  opening, a phone already subscribed with this PC's key reads as on and tells the PC again (it may have dropped the
  phone after a 410).
- **In Safari, plainly**: on an iPhone or iPad not opened from the home screen the row says "On iPhone, alerts work
  only from the home-screen app (iOS 16.4 or later). In Safari, tap Share, then Add to Home Screen, and open Nirvana
  from there." Without PushManager anywhere else: "This browser cannot get alerts." Permission denied: where to turn
  it on.
- **What sends.** The watcher is one more listener on P39b's one `events.subscribe` (`spaces::Feed`), running only
  while a phone has alerts on; the feed then keeps running with no page open. Each list is compared with the last
  (`changes`): an agent that was in the list with another state and is now `done` or `needs` is one alert. Working
  and idle send nothing. An agent seen for the first time is not a change: its first state is where it starts (so a
  new space whose Claude first shows as blocked sends nothing; the owner is the one who just opened it).
- **Debounce**: the same agent and state within `DEBOUNCE` (5 s) of its last push is not sent again
  (`Debounce::allow`). Done, working, done in 0.8 s is one push (`a_flap_sends_one_push`). A different state is
  news: needs then done in 2 s are two pushes. Unmeasured cost: needs, answered, needs again within 5 s (a second
  prompt right after the first) sends once; the owner has the chat open at that moment.
- **The push**: title the space, body "<agent> is done" / "<agent> needs you", data the pane id, name and space for
  the tap. Headers `TTL: 3600`, `Urgency: high` for needs and `normal` for done, `Content-Encoding: aes128gcm`,
  `Content-Type: application/octet-stream`, `Authorization: vapid t=<ES256 JWT, aud the push service's origin, exp now
  + 12 h, sub SUBJECT>, k=<public key>`.
- **Sending**: ureq, on the watcher's own thread (never the tokio runtime), `PUSH_TIMEOUT` 10 s, `redirects(0)` (a
  redirect would POST to a URL the allow-list never saw). 2xx is sent; **404 or 410 drops that phone** and rewrites the
  phones file; anything else is logged with the push service's host and the status, and the phone is kept.
- **Welcome push (my addition)**: a phone that turns alerts on for the first time gets one "Nirvana / Alerts are on
  for this phone." off the route's thread. It is §5 step 5's "first push" without waiting for an agent, and it
  proves the key, the encryption and Apple's acceptance of the token in one tap.

## Keys and phones (item 4)

- `nirvana-remote-vapid.key` (the VAPID private key, PKCS#8 v1, base64url) and `nirvana-remote-alerts.json` (each
  phone's endpoint, `p256dh`, `auth`, when added) in `crate::session::data_dir()`, beside `nirvana-remote.json`: for
  the owner, `%APPDATA%\herdr\sessions\nirvana\`. Outside every repository.
- **ACL**: each file is created new (`CREATE_NEW`, then renamed into place, which keeps the file's own descriptor)
  with the DACL of herdr's own pipe, `D:P(A;;GA;;;SY)(A;;GA;;;OW)`: protected (nothing inherited from the profile's
  folder, so no Administrators or other entry) and full access for SYSTEM and the file's owner only. Read back from
  the file system in the test as `D:P(A;;FA;;;SY)(A;;FA;;;OW)` for both files (GA reads back as FA for a file).
- **Never logged, never served**: what the key file holds is never put in an error or a log line (errors carry the
  `io::ErrorKind` only); `Vapid`'s `Debug` prints the public half. No route answers anything but the public key; the
  test checks `/api/alerts`, `/`, `/sw.js`, `/alerts.js` and the manifest for the file's text. Log lines name a push
  service's host only, never an endpoint's path (the phone's capability) or ureq's own error text (which carries the
  URL).
- Made once: a second open of the same folder has the same key, and the phones survive a restart. A key file that
  cannot be read turns alerts off with the reason in herdr-server.log; the rest of Nirvana Remote serves, and the
  routes answer 409 "alerts are not set up on this PC".

## Only the owner's phones (item 5)

- Every alerts route and file is dispatched after `Site::route`'s checks: the Tailscale service's connection, exactly
  one owner login, another device's address, this PC's Host, and for a POST `Sec-Fetch-Site`/`Origin` from this page.
  `a_refused_caller_gets_nothing_from_the_alerts_routes`: another login, no login, the owner's login from this PC's own
  address, a cross-site POST, a POST with neither header, another Host, a cross-site read of `/api/alerts`, another
  login's read of `/api/alerts` and of `/sw.js`: each 403 or 421 with the refusal text and no key; no phone added, no
  file written, nothing pushed. Control `p39e_after_checks` moves the dispatch above the checks.
- **SSRF**: the endpoint must parse as a URL, be `https`, have exactly a host in `PUSH_HOSTS`, no port other than the
  default, no user or password, no query or fragment, a path, and be at most 2 KiB. `PUSH_HOSTS`:
  - `web.push.apple.com` (Apple: Safari and every iPhone browser),
  - `fcm.googleapis.com` (Google FCM: Chrome and Edge on Android),
  - `updates.push.services.mozilla.com` (Mozilla autopush: Firefox).
  Refused in the test: `http:` to Apple, `web.push.apple.com.evil.example`, a path naming Apple on another host,
  `user@`, `user:pw@`, `:8443`, a query, a fragment, no path, `127.0.0.1`, `[::1]`, `localhost`, the PC's own
  `http://127.0.0.1:7790/api/send`, `file:`, no scheme, empty, 3000 characters. Tests use `Hosts::Local(port)`, a
  variant that exists only under `#[cfg(test)]` and lets through `http://127.0.0.1:<that port>` only; no test can name
  a real push service as a place to send.
- The phone's keys: `p256dh` 65 octets, `0x04`, and on the curve (an ECDH with a throwaway key); `auth` 16 octets.
- **Cap**: `MOST` = 8 phones; the ninth is 409 "8 phones already get alerts from this PC: turn alerts off on one of
  them first"; a phone already there may update its keys at the cap. Dead phones leave at their first 410.
- **Unsubscribe**: `POST /api/alerts/unsubscribe {"endpoint"}` removes it (`removed: true|false`), for any caller
  who passed the checks and knows the endpoint.

## What leaves the tailnet (item 6)

The push goes PC to Apple (`web.push.apple.com`) to the iPhone, over the internet, not the tailnet. Apple sees: the
endpoint (its own), the ciphertext and its length, the headers above, and the VAPID token: this PC's public key, the
audience `https://web.push.apple.com`, an expiry, and `sub` = `https://github.com/fahim-mygithub/nirvana-herdr` (the
fork's public repository; no e-mail address is in any token; review round S1). The body is encrypted end to end to the phone's key (RFC 8291) and holds only
the space's name, the agent's name, its state, and its herdr pane id (for the tap). Nothing from the agent's screen,
transcript, tool calls or folder is in it.

## Review round

From the review `p39e-review.md` on c8f72753, by "Opus high - P39e review round", 2026-11-05. Each finding was
checked against the code first; all four should-fix findings held as written.

- **S1, the VAPID `sub`.** `webpush::SUBJECT` is now `https://github.com/fahim-mygithub/nirvana-herdr`, the fork's
  public repository: an `https:` URL on a real public host, which is what the public reports show Apple accepting, and
  no e-mail address in any token sent to Apple. The test now names the URL and checks there is no `@` in it; before,
  it compared the claim with the same constant, which proved nothing. **Apple's acceptance is not measured.** It is the
  owner's first live check (step 5 below). A `status 403` in herdr-server.log on the welcome push
  (`nirvana remote welcome alert not sent ... status 403, the token refused`) would mean Apple's `BadJwtToken`: Apple
  refuses the token, most likely its `sub`. The fix then is the one constant.
- **S2, a new key.** `load_key` uses `Path::try_exists`, so an error while looking at the file is not "missing":
  alerts turn off with "the alerts key could not be looked at: <kind>", and no new key is renamed over the old one.
  When a key is made while phones are stored, the phones are dropped (memory and file), and a warning says why: each
  was subscribed with the old key, so the push service would refuse every alert to them. A phone whose push service
  answers 401 or 403 twice in a row (`REJECTED_MOST`) is dropped. A 2xx clears its count. The count is kept in memory
  only, so a restart starts it again. On opening, the page asks the PC (`POST /api/alerts/check`, which writes
  nothing). If the PC no longer keeps that subscription, or the phone's subscription was made with another key, the row
  says "The PC's alert key changed: turn alerts on again." and the next tap makes a fresh subscription.
- **S3, sending.** `push_all` sends to each phone on its own scoped thread. There are at most `MOST` (8) phones, so
  at most 8 threads, and one alert takes about one `PUSH_TIMEOUT` (10 s) at most, not one per phone. `stop` is
  checked before each phone is started. **What holds now about stop:** the watcher ends within `WAKE` (1 s). If an
  alert is being sent, it ends once that alert's pushes in flight are answered or time out (10 s at most, since they
  run at the same time), and no new phone or alert is started after `stop`. The server's stop does not wait for the
  watcher. Not covered: ureq's timeout covers the request. Whether it also bounds the DNS lookup on Windows is not
  measured.
- **S4, the tag.** `sw.js` tags a notification `agent-<pane>-<state>`, so "needs you" and then "done" are two
  notifications. With one tag per agent, iOS (no `renotify`) would show the second as a silent replacement.
- **N2.** `notificationclick` catches a rejected `focus()` and goes on to `openWindow(url)`.
- **N3.** The page posts `/api/alerts/subscribe` on opening only when the PC keeps the endpoint with other keys.
  When the subscription is identical, `add` does not rewrite the phones file (an older page may still post each time).
- **N5.** If the watcher thread panics, a guard (`Unwinding`) clears `running`. It clears the flag only while
  unwinding: a normal end already clears it in `go_on` under the phones lock, and clearing it again outside that lock
  could clear a newer watcher's flag and lead to a second watcher. **No test or control.** Nothing in the watcher can
  be made to panic from a test without a hook added only for that.
- **N1 (recorded).** The JS checks (`p39e_page_*`, `p39e_sw_*`, including this round's `p39e_sw_tag_state`,
  `p39e_sw_focus_fallback`, `p39e_page_key_changed` and `p39e_page_check_first`) assert the text of `alerts.js` and
  `sw.js`, not behaviour. They prove the line changed, not that a tap opens a chat or that iOS shows two banners.
  Steps 6-8 below are the only behavioural check.
- **N4 (recorded).** `redirects(0)` still has no test. "No test can name a real push service" holds because
  `Hosts::Local` is `#[cfg(test)]` on the variant and on its match arm, and it lets through `http://127.0.0.1:<port>`
  only. That is the guarantee. There is no compile-fail check of it.
- **N6 (recorded).** `PRIVATE_SDDL` grants `OW` (OWNER RIGHTS). A server that ever ran elevated would create files
  owned by Administrators, and a later non-elevated server (Administrators deny-only in its token) could not read its
  own key. Alerts would then be off with "could not be read", and no new key is made over it. Herdr's pipe has the
  same SDDL, so the risk is inherited.
- **N7 (recorded).** `ring` with `default-features = false` gets `alloc` (`generate_pkcs8`,
  `seal_in_place_append_tag`) through feature unification with rustls. If rustls ever stops enabling it, the build
  fails loudly; it cannot fail silently.
- **N8 (recorded).** The watcher's `before` list survives a listen error. After a herdr server restart, a reused pane
  id with another state could send one spurious alert, bounded by the debounce.
