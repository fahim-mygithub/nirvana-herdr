## Where blocked and the menu come from (reused, not new)

- **Blocked** is herdr's detector: `src/detect/manifests/claude.toml` rules `live_blocked_form` (:80),
  `dynamic_workflow_prompt` (:110), `mcp_elicitation_prompt` (:118), `bash_permission_prompt` (:164),
  `generic_permission_prompt` (:194) and `legacy_no_prompt_blocker` (:210) set `blocked`; the page's `needs` is that state (`spaces::status_word`,
  `src/nirvana_remote/spaces.rs:31`). Codex (`codex.toml` :7, :35, :58, :78, :92) and Antigravity
  (`antigravity.toml` :30, :38, :46, :55) have their own rules.
- **The menu** is the Running square's reader, `nirvana_running::prompt` (`src/nirvana_running.rs:213`), the one the
  window calls for a blocked agent (`src/client/shell/nirvana_mods.rs:1294`). Its fixtures are Claude Code 2.1.301's
  AskUserQuestion and Bash permission dialogs, measured 2026-10-16 (`nirvana_running.rs:8-15`), and the window answers
  with one digit and no Enter (`running_answer`, `nirvana_mods.rs:1301`). The phone presses the same digit.
- **Esc** is `agent.send_keys ["esc"]`, as P39b's "send now" (`live.rs`), `esc` being a herdr key name
  (`src/config/keybinds.rs:1315`).

**Which menus are buttons.** Claude Code's numbered menus only (`chat::is_claude`), and only when the last option is
the bottom of the screen: after it, nothing but rules and footer rows (`Esc to cancel`, `Enter to select`,
`Tab to amend`, `to navigate`), one of them naming Esc (`at_bottom`). Without that a numbered list Claude wrote above a
form with no numbers (an MCP elicitation's Accept/Decline) read as the menu: the first version of the guard counted
footer rows and let it through (test `a_screen_that_is_not_a_claude_menu_is_shown_raw_with_every_key` caught it).
**Every other agent's prompt is raw**: Codex and Antigravity are detected as blocked by herdr, but no screen of theirs
is in the tree and whether a digit picks without Enter there is not measured, so the phone shows their screen with
1 to 9, Enter and Esc and presses what the owner taps.

## A key only for the prompt the phone saw (item 4)

`GET /api/prompt` answers `seen`, an FNV-1a 64 hash: `menu\n` + the whole prompt (every row from the nearest full rule
above option 1 to the bottom, `❯` stripped, blank rows dropped; review round S3), or `raw\n` + the 24 bottom rows of
the screen. The sheet still shows the capped heading lines. `POST /api/key` reads the screen again (`agent.read`,
`source: visible`) and computes it again before anything is pressed:

| The agent now | The tap's `seen` | Answer |
|---|---|---|
| blocked, same prompt | equal | the key, if this prompt takes it (a menu: its digits and Esc; raw: all 11) |
| blocked, same prompt, pressed in the last 3 s | equal | 409 "already answered" (review round S2) |
| blocked, another prompt | differs, or null | 409 "the prompt changed on the PC" with the prompt now; the sheet redraws with it |
| not blocked | set | 409 "answered on the PC"; the sheet closes and says so |
| working | null, key `esc` | Esc; a second Esc to that pane within 3 s is 409 (review round S4) |
| idle or done | null | 409 "the agent is not working: nothing to stop" |

A menu takes no Enter: the parser drops the `❯` highlight, so an arrow key on the PC moves what Enter picks without
changing `seen`. The page also closes an open sheet with "Answered on the PC." when the live view says the agent left
`needs` without a tap from the phone.

**Not closed:** the few milliseconds between the server's second read and `agent.send_keys` (herdr has no
compare-and-press), and a prompt that comes back word for word (the same command asked again after the PC answered),
which hashes the same and takes the phone's key. A raw screen that changes faster than a tap (a timer on it) cannot be
answered from the phone: every tap gets 409 with the newer screen.

## The key table (item 5)

`prompt::KEYS`: `1`-`9`, `enter`, `esc`. The request names one; the name sent is the table's `&'static str`. A name
not in it is 400 before herdr is asked anything (`only_keys_from_the_table_reach_send_keys`: `ctrl+c`, `C-c`, `a`,
`10`, `0`, `1\r`, `enter enter`, `ESC`, `esc `, a raw ESC byte, empty, `tab`; the fake's call log is unchanged).
Each name in the table parses as a herdr key (`parse_key_combo`). Both routes run after P39a's and P39b's checks:
`a_refused_caller_gets_nothing_from_the_prompt_routes` (another login, no login, the owner's login from this PC's own
Tailscale address, a cross-site POST, a POST with neither header, a cross-site read, another Host; herdr is asked
nothing). Controls `p39c_key_after_checks` and `p39c_prompt_after_checks` put each route before the checks.

## The flaky test (item 6)

`raw()` did `let _ = stream.read_to_end(...)`, so a read error handed the test whatever had arrived. It now fails on
a read error with the error, its kind and the first bytes, and names the address when `connect` fails. **Corrected
in the review round (S1):** it was also said to fail a body whose length is not its `Content-Length`; in b7978b5e that
check never ran (the CR LF CR LF literal had been written as two raw LFs, so `windows(4)` never matched). It runs now,
and control `p39c_whole_checks` proves it.

**Reproduction, measured 2026-11-05 on this PC:**
- A probe test: one server, 64 threads × 60 GETs of `/app.js` and `/chat.js` alternately, 24 threads spinning the
  CPU, every body checked against its `Content-Length` and every read error kept. Alone: 3840 of 3840 whole.
- Eight copies of that probe at once, three rounds: 18 of 24 runs read 3840 of 3840 whole (about 69 000 answers, none
  short, no read error). The other 6 failed at `TcpStream::connect` with os error 10055 (WSAENOBUFS, "the system
  lacked sufficient buffer space or because a queue was full"): `netstat` counted 118 930 TIME_WAIT rows, back to 108
  about three minutes later. That pressure was the probe's own, machine-wide, while it lasted.
- The probe inside 15 runs of the `nirvana_remote` filter: 6 runs failed the probe. Their messages were not captured
  (nextest kept them, I filtered them out); 20 later runs, captured, passed. Given the 10055 runs, the likeliest
  reading of those 6 is the same port pressure, not a short body: *not proven*.
- Reading of the server (`http::finish`): the whole answer is written, the sending half shut (a FIN after the data),
  and what the caller sends is drained for up to 1 s, so the close is not a reset; Windows' default close with an
  empty receive buffer is graceful even when the drain times out. Nothing measured contradicts it.

**Verdict.** Not a server truncation that tailscaled could see: none in about 73 000 parallel reads under CPU load.
The test's failure at the 0.56.0 merge was not reproduced and its message was not kept, so its cause stays open; the
two causes seen in the lab are both outside the server (connect failing under port pressure, and a read that would
time out at 10 s). With `raw()` fixed, the next one names itself. No server code changed.
`asset_reads_in_parallel_arrive_whole` keeps a small version (16 × 24 = 384 connections, so it does not press on the
ports) and checks every body byte for byte; control `p39c_asset_whole` writes half of each answer and the test goes
red.

## Where the order or the plan was wrong or open

1. **"A fixed Esc button"** is drawn where the prototype draws it, in the composer row, and, as there, only while the
   agent works (`cur.working` in the prototype's markup). While it needs you, the sheet has its own Esc row and the
   row shows an Answer button that opens the sheet again after it was dismissed. If "fixed" meant always on screen,
   that is one line in `prompt.js` (`esc.hidden = ...`); the server already refuses Esc to an agent that is not
   working.
2. **The order's item 6 framing** ("a partial body is asserted on") is one possible reading. The lab showed the
   other one too: `connect` failing under port pressure, which the old `raw` reported as a panic at its `unwrap`,
   not as a short body. Which one hit the merge run is not known (no log kept).
3. **"Cover Claude Code's numbered menus at least; say which other agents' menus you recognise"**: none as buttons
   (above). herdr recognises Codex's and Antigravity's prompts as blocked; the phone shows them raw.
4. **The plan's §2.4** says a tap "sends that choice's key". For a Claude menu that is the digit alone, no Enter, as
   measured for the Running square. An option that opens a text box ("No, and tell Claude what to do", "Type
   something.") leaves Claude waiting for text; whether herdr still reads it as blocked, which would make P39b's send
   refuse it (409 blocked), is not measured.
